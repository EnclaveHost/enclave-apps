# Native applications through the standard OpenCL interface

The historical compatibility experiments below now feed the separately
packaged 0.6.9 candidate running in the confidential VM. See
`STANDARD_PACKAGE.md` for current deployment evidence and remaining gates.
The original CPU-only compatibility findings below are historical. Real Qwen
and Stable Diffusion now also execute authenticated Q8 work through masked
Shield exchanges in host containers, without a raw GPU device. See
[masked Q8 execution](../opencl/Q8_MASKED.md) and
[standard SD integration](STANDARD_SD_MASKED.md) for current evidence and limits.

The purpose is to exercise the standard GPU API applications actually use,
including native CPU fallback for operations outside the masked contract.

## Findings and changes

The pinned llama.cpp OpenCL backend initially rejects the Shield device by
name. `llama-shield-opencl.patch` permits the known logical device to use the
existing subgroup implementation after checking required extensions and both
16- and 32-lane subgroup sizes. Existing FP16/OpenCL-version checks remain.
The internal `INTEL` algorithm selector does not change the device's advertised
vendor or identity. This patch grants no public-data approval or offload plan.
Baseline device discovery returned no devices; the patched plugin discovers
`GPUOpenCL` with the existing truthful logical-device name.

With one OpenCL layer requested, real Qwen loading then failed because PoCL's
kernel library lacked `read_imageh` for a 1D buffer image. PoCL advertises FP16,
but this function was absent from its implementation. The corresponding
[Khronos image-read specification](https://registry.khronos.org/OpenCL/specs/unified/refpages/man/html/imageReadFunctions.html)
and [samplerless reference](https://registry.khronos.org/OpenCL/specs/unified/refpages/man/html/imageSamplerlessReadFunctions.html)
describe half-image operations under `cl_khr_fp16`.

`../opencl/pocl-half-images.patch` adds half-image reads and writes by reusing
the CPU runtime's existing float image addressing, channel conversion and
filtering. Reads use `vstore_half4_rte` for the final half conversion. Writes
promote half values exactly to float before the existing image write. No image,
texture or framebuffer is sent to a physical GPU by this implementation.

`test_half_images.cpp` fails against the baseline library with missing symbols.
It passes 78 cases against the patched bitcode across 1D, 1D-buffer, 1D-array,
2D, 2D-array and 3D images. Reads cover half, UNORM8 and SNORM8 storage,
samplerless read-only/read-write access, and nearest sampling with integer and
floating coordinates. Writes cover half storage with write-only/read-write
access. Expected half bits are calculated independently using the Khronos host
conversion header. The test is not full image conformance: linear filtering,
special floating-point values, denormals and normalized-format writes remain
untested. The [write reference](https://registry.khronos.org/OpenCL/specs/unified/refpages/man/html/imageWriteFunctions.html)
defines those additional cases.

The first implementation called an internal `convert_half4_rte` symbol absent
from this PoCL library. The tested patch uses its available explicit-rounding
store primitive instead. One test accidentally observed bitcode before its
optimization process completed; that result is excluded. The 78-case pass
was obtained after confirmed successful build completion.

## Half-precision math and conversion repairs

The next application failure was `_Z8_cl_tanhDh`. This build enables SLEEF,
so its active implementation is `sleef/libm/sleef_glue.cl`, not `tanh.cl`.
`pocl-half-tanh.patch` evaluates half tanh through the existing float function
and rounds once with `vstore_half_rte`; scalar and 2/3/4/8/16-wide overloads
are supplied. `test_half_tanh.cpp` exhausts all 65,536 binary16 encodings at
all six widths. All 393,216 evaluations passed with zero ULP difference from
an independently converted double-libm reference, consistent NaN classification,
and bit-identical scalar/vector output. This is not a formal correctly rounded
math proof. The old runtime fails the same test with the missing symbol.

Qwen then reached `_Z20_cl_convert_half_rtef` in its softplus kernel.
`pocl-half-convert.patch` adds explicit float-to-half conversion functions in a
separate source file, avoiding hand edits to autogenerated `convert_type.cl`.
It uses existing rounding stores for rte/rtz/rtp/rtn and all six vector widths.
Both the generic and SLEEF source lists include the new file.
`test_half_convert.cpp` covers every finite half value, the float immediately
below/at/above every adjacent-half midpoint (including overflow), both signs,
float extrema/subnormals, random float bit patterns and NaNs. Its 321,542 inputs
across 24 combinations produced 7,717,008 passing conversions, exact against
Khronos host conversion functions. NaN payload identity is not an API guarantee;
the test requires NaN classification and scalar/vector consistency. This does
not claim exhaustive coverage of all 2^32 float inputs or other source types.
The old runtime fails with the same missing conversion symbol.

The 78 half-image cases still pass after the tanh repair. Neither math repair
changes the offload recognizer or makes these operations eligible for masked GPU
execution; they implement the trusted local portion of the normal GPU API.

## Compiler fix and correction to the earlier experiment

After the math repairs, Qwen aborted while eagerly compiling its half-precision
`kernel_conv_2d`. The standalone `test_kernel_build.cpp` reproduces that error
without loading a model: source compilation succeeds, then querying
`CL_PROGRAM_BINARY_SIZES` triggers work-group compilation and LLVM InstCombine
aborts. Both original fast-math and strict-math options fail. Disabling
optimization passes compilation only and was not adopted as a workaround.

`pocl-vectorizer.patch` adapts
[upstream commit 19dc70b](https://github.com/pocl/pocl/commit/19dc70bbe927a6f6210ccd45b6a4c2a49fe6da96),
also discussed in [issue 1608](https://github.com/pocl/pocl/issues/1608),
to pass the target machine and vectorization configuration to the new LLVM
pass manager while retaining the pinned source's legacy branch. With the
correct library loaded, the convolution compiler reproducer passes.

**Evidence correction:** the earlier `vectorizer/` and `conv2d-patched.log`
experiments mounted `libpocl.so.2.13.0`, but this image contains separate regular
files for that filename and `libpocl.so.2`. Its ICD loads the latter. Those runs
therefore used the old library and did not test the proposed backport or the
extra-iteration candidate. Their claim that the backport failed, and their
claim to validate math against that backport, were invalid. The original files
are retained as historical observations, explicitly superseded by the corrected
runs. Original half-math results remain valid: they mounted the active kernel
bitcode path correctly.

The corrected runs mount the actual ICD path `/opt/shield/pocl/lib/libpocl.so.2`
and verify SHA-256
`90e4f6a7bbbe32d6170ca9575f3ad2630d31cd21fe3427e63dcb0faf881bb2ee`.
The probe's new `--expected-pocl-sha` rejects the wrong library before launching
Qwen; its negative control exits with code 2. Diagnostic compiler instrumentation
and the extra-iteration candidate were removed. The clean rebuild produces the
same digest as the saved vectorizer-only binary.

`test_conv2d.cpp` executes the original pinned convolution source with its
original fast-math options against an independent NCHW reference. Five shapes
cover channel/spatial tails, padding, stride, dilation, batches and nonzero
buffer offsets. All 7,492 outputs match after half rounding, and output guards
remain unchanged. Inputs are dyadic values chosen so intermediate products and
sums are exact; this tests indexing and execution but is not broad floating-point
accuracy coverage. The full tanh, conversion and image suites also pass with
the correctly mounted backport. The selected Khronos CTS API tests pass 16/16,
events pass 30/30, and the existing negative callback-status test passes. This
is selected regression coverage, not full conformance certification.

## Real application results and next work

The CPU control generated `The capital of France is Paris.` in 0.966 seconds.
With a cold cache, the one-layer OpenCL run completed in 59.522 seconds and the
all-layer run in 65.366 seconds, each generating the same tested response.
Native logs report 1/25 and 25/25 layers assigned to `GPUOpenCL`, respectively.
These times include kernel compilation and are not an acceleration benchmark.
A single short response is not sufficient numerical equivalence or model-quality
acceptance. The logical GPU is still executing these workloads on PoCL's CPU.

A separate all-layer run using the validated cache collected 5,934 kernel
launches across 16 kernel names. Two Q8 kernels account for about 79% of the
summed kernel time: `kernel_mul_mm_q8_0_f32_l4_lm` (165 launches) and
`kernel_mul_mv_q8_0_f32_flat` (1,521 launches). Float/half attention matrix kernels
also execute. These are actual launch statistics, not a list of merely compiled
kernels. PoCL 6's cq profiler prints unscaled event timestamp differences under
incorrect `us` headings; the corrected receipt uses nanoseconds. Summed kernel
time is 4.932 seconds for that one run, distinct from total process wall time.

The next compiler work is to analyze these actual Q8 kernel layouts and typed
operations, connect eligible work to authenticated public-weight policies and
masked execution, and verify outputs and failure behavior. The existing exact
integer recognizer does not cover these floating-point accumulation kernels;
there is no implicit quantization or newly authorized offload. Broader Qwen and
SD numerical tests, performance, VM deployment, protected graphics, publishing
and nucbox acceptance remain open.

## Reproduction and evidence

Pinned inputs are llama.cpp `ddd4ec1428a6201e18975ea52b07c71e0f9aef26`
and PoCL `952bc559f790e5deb5ae48692c4a19619b53fcdc`. Work is isolated under
`work/shield-compat/llama-opencl-app` and `work/shield-compat/pocl-half-build`.
Original source/build directories and the live worker were not modified.

The GGML experiment copies the pinned `ggml/` tree, applies the llama patch
from its parent directory, and builds `ggml-opencl` through a wrapper project
containing `add_subdirectory(ggml)`. Its options are Release, shared libraries,
dynamic backends, `GGML_MAX_NAME=128`, OpenCL enabled, Adreno-specific kernels
disabled, embedded kernels enabled, native CPU tuning disabled and CUDA/Vulkan
disabled. The existing `enclave-kvm-shield-hip-builder:1` supplies the compiler,
OpenCL headers and loader. Builds use one CPU and a 2 GiB memory limit.

The PoCL experiment copies the existing private source/build directory,
applies the half-image, half-tanh and half-convert patches, and rebuilds the
generic x86-64 kernel bitcode target. The vectorizer experiment also rebuilds
`lib/CL/libpocl.so.2.13.0`. A clean reproduction can apply these patches to a fresh
export of the pinned PoCL source and then use the existing `build-pocl.sh`,
which also applies the previously validated callback patch. The experimental
patches must be explicitly recorded alongside those build inputs. Wait for
successful build completion before mounting an output. Use a fresh PoCL cache
for each changed runtime: rebuilding bitcode alone does not change PoCL's cache
identity. The old `package/` directory is not updated by targeted Ninja builds.

Run `probe_opencl_application.py --layers 1 --expected-pocl-sha DIGEST` inside
the 0.6.8 desktop container (use the verified digest above for this build)
with the experimental plugin directory at `/probe`, public models at `/models`,
the patched kernel bitcode over its installed PoCL path and writable `/evidence`.
For the vectorizer experiment also mount the rebuilt libpocl over its installed
`/opt/shield/pocl/lib/libpocl.so.2` path, and require its expected digest.
Use `/probe` as working directory. The probe verifies the model digest, loads
the normal CPU backend, limits files to 8 MiB and execution to 180 seconds,
and saves exit status, source/binary identifiers and native diagnostics.
Containers use `--network=none`, no GPU devices, two CPUs and 4 GiB RAM. There
is no host service socket, so these runs cannot demonstrate physical GPU work.

Compile `../opencl/test_half_images.cpp` with the existing builder, C++17 and
`-lOpenCL`; execute it in the desktop container through ordinary library
discovery, once with the baseline library and once with the patched bitcode.
This uses one CPU, 2 GiB RAM, no network and no GPU devices.

Exported evidence is `opencl-application-progress.json` and
`evidence/opencl-application/`: source patches, superseded compiler experiments, test/probe sources, baseline
and patched discovery, all application failure stages, the image test results,
source/binary hashes, builder image IDs and explicit remaining validation gaps.
# Subsequent Q8 lowering work

The experimental compiler now recognizes the two Q8/float kernel structures,
validates an initial launch/storage subset, and authenticates separated weight
codes/scales against the exact approved GGUF tensor bytes. Original-kernel CPU
execution and actual-model admission receipts are documented in
`../opencl/Q8_LOWERING.md`. These plans remain non-dispatchable; this does not
establish masked Qwen/SD execution through the standard OpenCL backend.
