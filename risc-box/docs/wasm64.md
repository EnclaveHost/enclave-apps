# RISC Box past 4 GiB: the wasm64 build

A wasm32 component addresses at most 4 GiB of linear memory. RISC Box keeps
a guest's RAM in that memory (plus the disk image, the framebuffer, and the
fork roots of every instance), so the wasm32 line caps a guest at roughly
1.9 GiB of RAM and a box at about 3 GiB of instances. The wasm64 build lifts
that: 64-bit linear memory, RAM_MIB_MAX of 64 GiB, INSTANCES_MAX_BYTES_DEFAULT
of 32 GiB, and the platform's memory ceiling for a memory64 component is the
deployment's whole RAM slice rather than the 4096 MB clamp.

`wasm64/build.sh` produces `risc-box64.wasm`, a memory64 wasip2 component.
`wasm64/prepare-toolchain.sh` builds what it needs once. This document is
the why behind both.

## There is no wasm64-wasip2 target

rustc has `wasm64-unknown-unknown` and nothing for WASI on wasm64. The build
uses a custom target spec (`wasm64/wasm64-wasip2.json`: the wasm32-wasip2
spec with a 64-bit arch, data layout and pointer width, and `-mwasm64` for
the linker) and builds std from source (`-Zbuild-std`) out of a copy of
this nightly's `library/` widened for wasm64 (`std-wasm64.sh`: six files
whose `target_arch = "wasm32"` gates mean "any wasm").

The C side is wasi-libc built for `wasm64-wasip2` with the platform's
memory64 patch (musl assumes 32-bit pointers in its atomics), installed as
the self-contained sysroot rustc links for the custom target. wasi-libc's
checked-in `wasip2_component_type.o` is a wasm32 relocatable carrying the
`component-type` custom section that types libc's WASI imports; wasm-ld
refuses a wasm32 object in a wasm64 link, so `regen_component_type.py`
compiles the same dummy function for wasm64 and splices the section back in.

The WASI bindings std uses (the `wasip2` crate, generated by `wit-bindgen`)
are pointer-size aware in their return areas, but every import is gated on
`target_arch = "wasm32"` and stubbed with `unreachable!()` otherwise, and
wit-bindgen's `cabi_realloc` runtime ships as a wasm32 object. Both are
patched copies (`patches/`), wired into the std workspace by `std-wasm64.sh`
and into the app graph by `build.sh`.

Three app-graph crates needed the same widening: `getrandom` 0.2 and 0.4
(WASI backends gated on wasm32), and getrandom 0.2 additionally reaches WASI
through preview1 `random_get`, which on wasm32 rustc satisfies with its
bundled adapter module. That adapter is wasm32 and addresses the app's
memory with 32-bit offsets; there is no wasm64 adapter. The patched copy
asks the wasi 0.2 `random` interface instead, as getrandom 0.3+ does. (A
same-named definition in the app does not catch it: wasm-ld keeps an
import-module'd undefined symbol apart from a definition of the same name.)

The vendored C (OPL3, ENet, minih264) is compiled by build.rs, which now
targets `wasm{32,64}-wasip2` by the cargo arch rather than assuming 32.

## The component encoder

rustc links a wasip2 component through `wasm-component-ld`, which hands the
core module to wit-component. wit-component typed every canonical pointer
as i32. `patches/wit-component-memory64.patch` makes it read the width from
the module's memory (import section first: a memory may be imported), and
`wasm-tools` built from that tree does the encode: rustc stops at the core
module (`--skip-wit-component`), then `wasm-tools component new`.

The wasip2 crate's metadata names its interfaces `@0.2.12` while wasi-libc's
names them `@0.2.0`; the encoder merges semver-compatible imports to the
newest version present, so the app component imports every interface at
0.2.12. That matters for the proxy.

## The host cannot be called from 64-bit memory

wasmtime 49 parses and runs memory64 components (`-W
memory64,component-model-memory64`; the engine errors "64-bit memories
require the `cm64` feature" without the second switch). But its host-side
typed canonical ABI — the `Lower`/`Lift` machinery every `wasmtime-wasi`
function is bound through — still reads pointers and lengths as u32
(wasmtime FIXME #4311). A wasm64 component calling `get-arguments` gets its
return area written in the 32-bit layout and reads garbage; anything living
above 4 GiB is truncated.

What the engine implements completely is the component-to-component adapter
(the FACT trampolines): a 64-bit caller and a 32-bit callee are transcoded,
including resource handles. So the app is composed on top of
`wasm64/wasiproxy`: a wasm32 component that imports every stable wasi 0.2.12
interface from the host and exports the same interfaces, forwarding each
call verbatim. `wac plug` links the app's imports to the proxy's exports; the
proxy's imports become the composed component's imports; the host only ever
sees a 32-bit caller.

`wasm-tools compose` cannot do this (it does not remap resource types across
the boundary, for a wasm32 app either); `wac` can, once built on the
wasm-tools crates that know memory64 components
(`patches/wac-wasm-tools-0.256.patch`).

The proxy is generated (`wasiproxy/gen.py`) from the resolved WIT: one
wrapper struct per exported resource holding the imported handle, one
`Guest` impl per interface, converters between the import-side and
export-side Rust types. `build.sh` regenerates it when the WIT moves and
refuses a composition in which any app import bypassed the proxy.

Costs: one extra copy per list or string crossing (the adapter copies
between the two linear memories) and one handle indirection per stream,
socket or pollable. For a machine emulator's socket traffic this is noise.

## What it costs the guest

The engine keeps explicit bounds checks on a 64-bit memory: the guard-page
trick that lets a 32-bit index skip the compare needs a reservation that
covers every reachable address, which a 64-bit index defeats. Measured on
the sample image (512 MiB guest, boot to the console marker, same box,
wasmtime 49):

| build | boot to marker |
| --- | --- |
| wasm32 (shared-everything-threads build) | 3.1 s |
| wasm64 | 4.6 s |
| wasm64, `-O memory-reservation=16G -O memory-may-move=n` | 4.3 s |
| wasm64, plus `-O memory-guard-size=8G` | 4.4 s |

Steady state says the same: the 5 GiB guest of the lifecycle test runs at
~52 MIPS where the wasm32 build's Alpine run on this workstation logged ~80.
About 1.5x on the interpreter's hot loop, and no launch flag buys it back
(the reservation and guard settings are within noise). So the wasm64 build
is for boxes that need the address space — a guest past ~1.9 GiB, or more
than ~3 GiB of instances — not a replacement for the wasm32 build.

## Running it

    wasmtime run -W memory64,component-model-memory64 \
      -W max-memory-size=<bytes> -Sinherit-network -Sallow-ip-name-lookup \
      --env ... risc-box64.wasm

The guest kernel has to be able to use the memory too. The sample image's
kernel (`images/fw_payload.elf`, Linux 5.4) was built with
`CONFIG_MAXPHYSMEM_2GB`: it maps exactly 2 GiB past its load address and
ignores the rest, whatever the device tree says, so a 5 GiB guest on it
OOMs at 2 GiB. The Alpine kernel from `guest/` (Linux 5.15, Sv39, the
128 GiB linear map) uses all of it; that is the kernel the fleet runs.

On the platform, the wasm manager sees a memory64 component (a component
whose main core module declares a 64-bit memory, `_component_mem64`), adds
the two switches, lifts the 4096 MB ceiling to the deployment's slice, and
refuses readably on an engine that cannot compile the memory64 component
probe. The gateway, CLI and site classify it the same way (`componentMem64`)
so the publish path stamps `mem64` on the contract.

## Proven

`scripts/snaptest.py --mem64 --ram 5120` with the Alpine kernel and headless
rootfs from R2: the guest sees 4945 MB, fills 4.4 GB of tmpfs, the engine
process reaches 5.4 GB resident, the snapshot (25.6 MB: 32k of 1.3M RAM
pages non-zero) resumes in 0.79 s, and the file's size and two checksums
are identical after the resume. docs/snapshot-handoff.md has the table.

## The platform builds this now

`wasm/Dockerfile.wasm64p2-build` in the enclave repo is the supported way to
build a >4 GiB guest, for C and for Rust, and it is the same recipe as
`wasm64/prepare-toolchain.sh` here plus compiler-rt builtins for wasm64 (a
C link needs them; Rust brings its own). The scripts in this directory stay
as the app's own development path — they are what the platform image was cut
from — but a publisher who is not hacking on RISC Box should use the image:

    docker run --rm -v "$PWD":/src --entrypoint enclave-wasm64-rust \
      enclave-wasm64p2-build . -o risc-box64.wasm

The older `Dockerfile.wasm64c-build`, which produced a portless
wasm64-wasip1 core module, is gone: one >4 GiB class now, and it is a
component.

## Reproducing the toolchain

`wasm64/prepare-toolchain.sh` (or `docker build -f wasm64/Dockerfile .`)
fetches and builds, into `$W64`:

| component | pin | patch |
| --- | --- | --- |
| wasi-sdk | 34 rc.2 (clang 23; wasi-libc's wasip2 build needs its `-fdefer-ts`) | — |
| wasi-libc | 6d8745c8, built `-DTARGET_TRIPLE=wasm64-wasip2` | `wasi-libc-mem64.patch` (the platform's) |
| wasm-tools | v1.256.0 | `wit-component-memory64.patch` |
| wac | 49bab231 | `wac-wasm-tools-0.256.patch` |
| wit-bindgen | 0.57.1 (std's) | `wit-bindgen-0.57.1-wasm64.patch` |
| wasip2 | 1.0.4 (std's) | cfg gates widened by sed |
| getrandom | 0.2.17, 0.4.3 | `getrandom-*-wasm64.patch` |
| rust-src | this nightly's `library/` | `std-wasm64.sh` |

Then `W64=... wasm64/build.sh`. The engine side needs nothing: wasmtime 49
as pinned by the platform already runs it.
